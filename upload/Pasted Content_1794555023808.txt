## 3.1 Fix the Mock provider selection defect

The current bridge selects the mock provider before any other provider:

`providers.FirstOrDefault(p => p.IsEnabled && p.Code == "mock")`

The mock provider reports itself enabled unconditionally.

This can cause OTP requests to report success without sending real SMS.

Fix provider selection and environment behavior.

Requirements:

- Development may use an explicitly configured mock.
- Production must never silently use a mock.
- Mock behavior must be explicitly selected by environment/configuration.
- An unavailable real provider must return a clear, safe failure.
- A successful mock response must never be confused with a real delivery.
- No provider should be considered production-ready without verified configuration and contract.

Add tests proving that a Production configuration cannot select the mock provider.

## 3.2 Remove the hardcoded OTP placeholder

Inspect `SmsIrProvider`.

The current implementation can use a hardcoded OTP value of `123456` when the request has no parameters.

Remove this behavior completely.

Never send:

- A hardcoded OTP.
- A placeholder OTP.
- An empty OTP parameter.
- A previous user's OTP.
- An OTP recovered from an unrelated challenge.

If the real OTP cannot be safely recovered, fail closed.

## 3.3 Replace Base64 OTP storage with protected payloads

Inspect `LegacySmsBridge`.

Base64 is not encryption.

Sensitive OTP payloads must be protected using ASP.NET Core Data Protection or an equally appropriate cryptographic mechanism.

Requirements:

- Do not store OTP plaintext.
- Do not store Base64 as if it were encryption.
- Use a stable and correctly scoped Data Protection purpose.
- Ensure Data Protection keys persist across application restarts and instances.
- Protect payloads only for the minimum required lifetime.
- Purge sensitive payloads after terminal processing.
- Never log OTP values.
- Never return OTP values from production endpoints.

## 3.4 Fix the Outbox processing lifecycle

The current implementation must be reviewed end-to-end.

The correct order is:

1. Generate OTP.
2. Create a protected dispatch payload.
3. Persist the outbox record.
4. Confirm persistence.
5. Claim the message atomically.
6. Recover and unprotect the payload.
7. Validate expiry and purpose.
8. Construct the provider request using the actual OTP.
9. Dispatch through the configured provider.
10. Persist the provider outcome.
11. Purge the protected payload when appropriate.

The current worker reconstructs a request with null parameters and does not recover the protected OTP.

Fix this completely.

Do not implement a workaround that simply stores the OTP in plaintext in `ParametersJson`.

## 3.5 Make SMS dispatch durable

The current `Program.cs` registers:

- `InMemorySmsOutboxStore`
- `InMemoryPaymentStore`

These are not suitable as the active Production stores.

Wire the correct durable PostgreSQL implementation for Production, with explicit environment-aware registrations.

Requirements:

- Atomic message claiming.
- Unique tenant/idempotency constraints.
- Lease recovery.
- Expiry handling.
- Retry with bounded exponential backoff and jitter.
- Correct handling of ambiguous provider outcomes.
- Dead-letter handling.
- No blind retry after an ambiguous successful submission.
- Correct provider selection.
- Multi-instance safety.

Use the in-memory implementation only in isolated Development/Test configurations.

Do not claim exactly-once delivery to a third-party provider.

# 5. AbrIT Drive — Replace Folder Provisioning With Nextcloud User Provisioning

The current implementation in:

- `Drive/AbrITDriveOptions.cs`
- `Drive/DriveController.cs`
- `Drive/DriveStatusService.cs`

uses one technical Nextcloud account and one WebDAV folder per Orchard user.

This does not satisfy the new Drive integration guide.

A folder under one shared technical account is not equivalent to a dedicated Nextcloud user with an independent quota.

Implement the Nextcloud User Provisioning API.

## 5.1 Official API contract

Use the official Nextcloud documentation:

`https://docs.nextcloud.com/server/stable/admin_manual/configuration_user/user_provisioning_api.html`

Relevant base path:

`/ocs/v1.php/cloud`

Required request header:

`OCS-APIRequest: true`

Use an appropriate `Accept: application/json` header and correctly encode POST/PUT request bodies as `application/x-www-form-urlencoded` where required by the official API.

Do not assume WebDAV is a substitute for the Provisioning API.

## 5.2 Required operations

Implement a dedicated server-side Nextcloud client abstraction supporting:

### Create user

`POST /ocs/v1.php/cloud/users`

Support:

- `userid`
- `password`
- `displayName`
- `email`
- `quota`

### Retrieve user

`GET /ocs/v1.php/cloud/users/{userid}`

Retrieve:

- User ID.
- Enabled state.
- Email.
- Display name.
- Quota.
- Available quota data where supported.
- Used storage.
- Other necessary account status fields.

### Update quota

`PUT /ocs/v1.php/cloud/users/{userid}`

Use the documented `key=quota` and `value=...` fields.

### Enable user

`PUT /ocs/v1.php/cloud/users/{userid}/enable`

### Disable user

`PUT /ocs/v1.php/cloud/users/{userid}/disable`

Handle all OCS meta status codes, not just HTTP status codes.

In particular, handle duplicate usernames (OCS status code 102) safely.

Do not treat an HTTP 200 response as proof that an OCS operation succeeded. Parse and validate the OCS response metadata.

## 5.3 Dedicated account identity and persistence

Create a durable mapping between the Orchard customer and the Nextcloud user.

Persist at least:

- Orchard user ID.
- Nextcloud user ID.
- Provisioning status.
- Assigned quota.
- Last known used storage where appropriate.
- Last successful synchronization.
- Last error category.
- Retry/operation metadata.
- Creation timestamp.
- Update timestamp.

Add database constraints ensuring one customer cannot accidentally create multiple unrelated Nextcloud accounts.

Use versioned migrations.

Never store Nextcloud passwords in plaintext.

Do not expose administrative Nextcloud credentials to customer-facing code.

## 5.4 Credential design

The Drive guide requires a username and password for the Nextcloud account.

Design a safe credential flow.

Requirements:

- Do not automatically reuse the Orchard portal password without explicit product approval.
- Do not store the Nextcloud password in plaintext.
- Never log passwords.
- Never expose the administrator's Nextcloud credentials.
- Never return an administrator token or Basic Authorization header.
- Provide a safe customer credential setup or initial credential delivery mechanism.
- Do not display the password again after its permitted one-time display.
- If password recovery or password changes are required, use a dedicated secure flow.

If the business requirement does not specify whether the customer chooses the Drive password or receives an initial generated password, identify this as a product decision. Do not silently choose an unsafe implementation.

## 5.5 Provisioning idempotency

Repeated requests must not create duplicate Nextcloud users.

Implement an idempotent workflow:

1. Load the Orchard customer.
2. Load the persisted Nextcloud mapping.
3. Verify that the requested account belongs to that customer.
4. If an account is already mapped, retrieve it from Nextcloud.
5. Reconcile its quota and enabled state when appropriate.
6. If no mapping exists, create the account.
7. Persist the mapping only after validating the external response.
8. If a duplicate username is reported without a trusted mapping, do not adopt the existing account automatically.
9. Handle network timeouts and ambiguous responses through reconciliation.
10. Make repeated provisioning requests safe.

Do not create duplicate accounts when the external request succeeds but the local database update fails.

## 5.6 Quota management

The initial acceptance test uses 100 MB.

Implement a proper quota model.

Requirements:

- Store the quota as an explicit value.
- Map plan quota values to valid Nextcloud quota strings.
- Support quota changes after plan changes.
- Verify the quota after updates.
- Do not report success until the external account reflects the expected quota.
- Correctly handle unlimited quota and invalid quota values.
- Never infer a customer's personal quota from the technical account's shared storage.

For the initial test, the customer must receive a dedicated Nextcloud account with a verified 100 MB quota.

## 5.7 Account status and storage usage

Retrieve the real Nextcloud account status.

The customer portal must show:

- Account state.
- Drive URL.
- Nextcloud username or account identifier.
- Assigned quota.
- Used storage.
- Available storage where supported.

Display a real external link after the account is ready.
