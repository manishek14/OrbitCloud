# AbrIT Portal — Order access (Phase 2)

## Server authorization

`OrderAuthorizationHandler` is a tenant-scoped Orchard `IAuthorizationHandler` for `PermissionRequirement`. It checks every `AbrITOrder` content resource, and also type-only authorization requests. It calls `context.Fail()` for anonymous users, missing stable IDs, nonowners, drafts, and customer write operations. A fail remains effective even if the broad `ViewContent` role grant ran first. Administrators with the actual `Administrator` role retain access. Other content types, including `AbrITService`, retain their normal Orchard grants.

Customer ownership is `ContentItem.Owner`, matched ordinally to the authenticated `ClaimTypes.NameIdentifier` (Orchard's stable user ID). It is not inferred from email, display name, `User.Identity.Name`, or caller parameters. Existing orders with a missing or mismatched Owner remain unavailable to customers; an administrator must reconcile legacy ownership against trusted records before exposing them.

Orchard's `ItemController.Display` authorizes the loaded ContentItem through `CommonPermissions.ViewContent`. The handler therefore protects direct content URLs and aliases that reach that controller. The test harness exercises the real Orchard controller over HTTP using in-memory content and a test-only authentication scheme. It does not register this scheme in the portal.

The existing `MyOrders` query is preserved by name but uses `AbrITOrders`, a tenant-scoped query source. It ignores caller parameters, filters `ContentItemIndex` by published order type and stable owner ID, caps results at 100, and performs a second authorization check for each returned order. `AbrITOrder` is intentionally excluded from the public Lucene `search` index; no customer email or order fields are added to the public index. The public catalog index still includes `AbrITService`.

## Verification

The standalone test executable runs 31 assertions: anonymous denied; customer A reads A and is denied B; customer B reads B; administrator reads B; missing owner/ID and draft denied; name spoofing denied; customer edit denied; service catalog remains public; type-only order access denied. Both authorization-handler registration orders are exercised. HTTP checks return 401 for anonymous, 200 for an owner and administrator, and 403 for nonowners and an alias. Final run: 31 passed, 0 failed. Run command is in `BASELINE.md`; result is in ignored `artifacts/development/security-test.txt`.

The development tenant was also exercised through Orchard Query APIs: catalog=1, `MyOrders` anonymous=0, owner=1, unrelated=0. Only the cloned development database was used.

## Remaining controls

- Content queries written by administrators are trusted code and may bypass content-item display authorization if they directly render order fields. Query management permissions and all templates must be reviewed before publishing new queries.
- Existing published orders may have been created by administrators. Stable ownership is taken only from the actual `Owner` field. Reconciliation of historical records is a separate, audited data task.
- Native Orchard administrative edit, preview, API, and GraphQL paths should receive full integration testing on a clone before production release. The custom handler vetoes content-item authorization, while some back-office query/render paths may not load a content resource.

## Phase 3 customer identity, dashboard and catalog

- The public `Content-ServiceCatalogPage.Detail.liquid` no longer references `AdminAllOrders` or any order query. No unrestricted administrative order query or view was created. Orchard administrator access to order content remains subject to its administrative permissions and the Phase 2 order authorization handler.
- Native Orchard 3.0.1 Users registration, reset password, change email, local login and email features were enabled only in the cloned development tenant. Registration requires email verification; Orchard's built-in Authenticated role is used after login. No parallel user store or authentication scheme was introduced. Reapply safely to the isolated tenant with `ASPNETCORE_ENVIRONMENT=Development`, `ORCHARD_APP_DATA=../artifacts/development/App_Data`, and `dotnet run --project AbrITPortal/AbrITPortal.csproj --no-build --artifacts-path artifacts/build -- --abrit-identity-setup`. The command refuses databases without the `abrit_portal_dev_` prefix. The feature-only recipe `AbrITPortal/Recipes/DevelopmentIdentity.recipe.json` is version controlled and contains no customer content or credentials; the guarded command applies the development-only settings.
- `/dashboard` and `/account` require authorization. Dashboard orders come solely from the Phase 2 `MyOrders` query, which uses the stable Orchard user ID and content authorization; the dashboard independently rejects any result with a different owner, unpublished status or wrong content type. The public catalog uses the existing `AllServices` query and never loads customer orders. Service details accept only a published `AbrITService` found in that query. Purchase controls are disabled and clearly marked as under development.
- Account information comes from Orchard `UserManager<IUser>`; native ChangeEmail and ChangePassword remain the only account update paths. Password recovery and reset use Orchard's built-in routes and require a functioning email provider. The current local pickup is development only. Administrator must configure a real SMTP provider, sender and email deliverability before customer email verification can operate outside development.
- HTTP registration with a random account and local pickup was observed; confirmation and subsequent login reached authenticated dashboard and account pages. Native logout returned the session to Login. Password recovery produced a local reset email; after reset, the new password authenticated successfully. The 43 automated assertions cover existing order authorization and dashboard data isolation, but do not replace a full authenticated browser session test.

## Phase 5 — AbrIT Drive status and provisioning

- `/drive` (GET) and `/drive/provision` (POST) both carry `[Authorize]`. The harness exercises them over HTTP with the fixture scheme: anonymous requests are rejected (401 in-process; a 302 to `/Login` behind the real authentication middleware), and the provision action additionally requires the Orchard antiforgery token — a POST without the token returns 400. Every rendered page also embeds the antiforgery token through the shared shell, matching the Phase 4 pattern.
- The portal talks to AbrIT Drive (Nextcloud) with one technical account configured server-side. Customer-facing pages never receive, display or link the Drive credentials; the harness asserts the app password and its Basic header appear nowhere in any rendered state (missing, ready, unreachable).
- Per-customer folders are provisioned under the technical account's `CustomerRoot` as `u-<16 hex>` — a SHA-256 fragment of the stable Orchard user id. Raw user ids, usernames, phone numbers and emails never leave the portal, folder names are stable and collision-free for the portal's scale, and the page never renders the internal folder name (asserted).
- Provisioning is idempotent and least-surprise: `MKCOL` for the customer folder; HTTP 405 (already exists) and 201 are both accepted; on 409 the root collection is created once and the folder retried. After provisioning the per-user cache entry is removed and the status re-read from the server — the page never fabricates a Ready state.
- Status rendering is honest by design: `NotConfigured` (integration off), `Missing` (404 — offers activation), `Unreachable` (network failure, non-2xx, refused plain HTTP, or bad credentials — with static, non-leaking detail text), `Ready` (207 with RFC 4331 quota properties). Exception text is never rendered; detail strings are fixed literals.
- Credentials travel only when `BaseUrl` is HTTPS, or in Development, or with an explicit `AllowInsecure` opt-in; production plain HTTP is refused before any request is made. The typed HttpClient clamps the per-request timeout to 1..30 s and caps connection lifetime (2 min) / idle time (30 s) so a restarted Drive server cannot leave poisoned keep-alive connections that would fail non-idempotent MKCOL requests.
- Status responses are cached per user (`abrit-drive:<userId>`, default 60 s, clamped 0..600) to bound the request rate against Drive; provisioning bypasses the cache. The WebDAV quota XML is parsed by a pure static helper (`Interpret`/`Quota`) covered by harness assertions for 207, 404 and 401 responses.
- The harness's Phase 5 block runs a live in-process WebDAV stand-in (Kestrel): it verifies the folder is really created on the DAV server after the browser-equivalent POST, that provisioning cannot be triggered without a token, and that the earlier order-security guarantees (anonymous denial, ownership checks, 403 for non-owners) still hold with `MapControllers` enabled. 72 assertions, 0 failures.
- Remaining controls: the technical account should be dedicated to the portal with quota and permission limits on the Nextcloud side; customer-facing file upload/download through the portal is intentionally not implemented; production rollout needs the real Nextcloud origin, an HTTPS certificate and administrator-managed credentials.
